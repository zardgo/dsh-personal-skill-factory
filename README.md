# DSH Skill Factory v0.3.10（最终 Skill 组合优化候选版）

> 保留通用 Skill Architect 的业务模型，不对 OKR 书籍做特例；**仍需在用户 Mac 的真实 DSH 中验证**。不裁剪整本书，也不将不同任务为了凑 Skill 数量而合并。

## v0.3.10 更新：Skill Portfolio Optimizer

- 在能力簇规划后，新增独立的「最终 Skill 组合优化」层。对 3 个及以上可新建/合并能力自动运行；旧规划可在工作台一键补做优化，**不需重新导入或重新解析书籍**。
- AI 按共同业务目标与使用角色推荐最小充分的 Skill 组合，不硬编码某本书或一个固定 Skill 数量。不同角色、权限不确定及上下文未完整展示的能力禁止自动合并；既有 REUSE / REFERENCE / REJECT / ENHANCE / SPLIT 决策受到保护。
- 自动验证每个候选能力恰好出现一次；优化失败会标记待复核并阻断默认按能力簇逐个生成。原始任务、来源证据和模型审查记录保持不变。
- 页面默认只展示最终推荐卡片及理由；原始能力簇、任务与证据收纳进折叠的高级审核区。需要人工覆盖时才展开逐项修改。
- 默认生成蓝图时由 **服务端** 根据已批准的优化分组展开，而不是仅通过页面视觉归并；生成、Evals 与发布审批仍单独保留。
- 本地 51/51 项离线测试通过，未在用户 Mac 上进行真实 DSH UI 或《这就是OKR》整本模型验收。模型给出的角色/权限解释仍需人核实，不能视为真实权限清单。

## v0.3.9 更新：分层任务归并

- 修复全书分批完成后候选任务超过 50 个即停止规划的问题，改为**有界去重分页 → 任务能力簇分层归并 → 全局 Skill 架构决策**。
- **任务 ≠ Skill**：原始任务、证据 ID、方法 ID 保留并可追溯；中间能力簇仅用于模型规划，最终展开回完整任务集合，不能丢失任何任务或反复归属。
- 分层处理逐页保存经核验的检查点；模型中断、Host 重启后按输入/模型/处理版本复用已完成的分析和归并分页。
- 安全门禁：禁止缺失、重复或未知任务引用；禁止把纯知识参考和可执行任务混为同一簇；不能合理收敛时阻止不完整规划，而非强行生成 Skill。
- 对同一长证据跨分批出现的**完全一致**任务去重，避免错误地把重复记录当成两个任务。
- 新增 90 任务分层规划及 78 任务缺失/恢复测试，当前 **42/42 离线自动化测试通过**，未完成真实模型端到端验收。

## v0.3.8 更新：模型超时恢复

- 将能力架构阶段原有固定 120 秒模型超时调整为受控的 240 秒；其他模型调用仍使用原来的默认时限。
- 各规划阶段使用更合理的输出 token 预算，不再固定要求 12,000 tokens。
- `MODEL_TIMEOUT` 最多自动重试一次；结构错误、证据错误等非暂时失败不会重试。重试状态在工作台可见。
- 单次任务发现、跨批次任务归并和已有 Skill 资产扫描均可在中断后复用已经验证的检查点。
- 兼容 v0.3.7 已保存的分批规划检查点；不覆盖原始书籍、分析结果、评测历史或 Skill。

## v0.3.7 更新

- **分批任务发现**：当证据、方法总量超出单次模型请求上限时，按有界输入自动分批；分批是模型处理策略，不是按章节拆成独立 Skill。
- **跨批次语义归并**：先整合多个批次的任务，再由统一 Skill Architect 进行全局 CREATE / REUSE / ENHANCE / MERGE / SPLIT / REFERENCE / REJECT 决策。
- **断点续跑**：每批完成后保存含输入与模型身份校验的检查点；中断后可复用已经完成的批次，不把未完成规划标为成功。
- **覆盖性保护**：所有任务必须在归并中有明确去向；不静默跳过超限证据。来源本身若标记截断，结果仍明确显示不完整。
- **规划进度**：后台任务报告分批发现、跨批次合并和资产盘点进度。

验证范围：**36/36 离线自动化测试通过（包含模拟模型）**；尚未完成用户真实 DSH + 整本 OKR 资料的端到端验收。历史项目和 Skill 发布状态保持不变。当前功能仍存在任务候选数量超过规划上限时阻断的保护逻辑，不保证任意体量输入均可无条件处理成功。

## v0.3.6 更新

> v0.3.6：资料分析后的候选方法统一送入 Skill Architect；推荐 Skill 数量基于任务边界，不按章节/方法机械生成。原有候选只读保留，旧直接派生 API 被阻断。人工可通过卡片合并、拆分或排除，不再要求编写 JSON。

## v0.3.5 的其他功能

> 基于用户提供的 v0.3.4 完整源码开发。保持 DSH 原生 Client + Host 插件架构；模型通过 DSH 已配置服务调用；不连接或更改其他业务工作台。

## v0.3.5 主要更新

- **独立关键风险质量门禁**：五种领域无关风险逐项检查；任务分数高不能掩盖风险失败，缺少风险判定也不能发布。
- **候选优化实验**：已有真实 Evals → 生成候选 → 冻结用例小批试跑 → 人工确认应用 → 新 revision → 全套回归。支持质量或效率优化，不改写测试计划，不自动发布。
- **右下角使用指南**：可最小化、关闭和重新打开，按页面提示操作、搜索常见问题；尽力保存显示状态。
- **触发工作区恢复**：已保存工作区与用例可重新读取，实际会话 ID 仍需要人工核验。
- **构建清理**：过滤 AppleDouble 文件，防止旧文件进入 npm 包。

```bash
npm run check
npm pack
# 完全退出 DSH；按需先备份 ~/.dsh/skill-factory
# dsh plugin --profile desktop remove dsh-personal-skill-factory
# dsh plugin --profile desktop add /path/to/dsh-personal-skill-factory-0.3.10.tgz
```

**数据目录**：`~/.dsh/skill-factory/`，不随插件移除自动删除。发布到个人 Skill 目录仍需当前版本门禁及人工批准。不要将业务数据、会话日志、任何秘钥上传到 GitHub。

## 借鉴与开源边界

# DSH Skill Factory 0.2.8 候选版

从 desktop profile 已安装的 0.2.6 包恢复可编辑源码。源码在 `src/`，构建复制到 `lib/` 并校验 Host、客户端与包版本一致。项目使用 Node 22.19 或更新版本。运行 `npm run check` 和 `npm pack`。

此版本为九字段生成添加格式示例、严格 JSON 解析、别名及列表规范化、最多两次定向修复和本地候选记录。无法补齐的草稿可以在源文档面板重新打开后人工填写。候选写入 `~/.dsh/skill-factory/proposals/`，保留请求编号、模型、字段错误与模型使用量（如提供商返回）。派生需要人工确认并校验当前父项目 revision、来源文档和所选方法。重复提交同一个候选会返回已有派生项目。

使用 desktop profile 安装本地包路径。先完整退出 DSH，再通过 `dsh plugin --profile desktop add "/完整路径/dsh-personal-skill-factory-0.2.8.tgz"` 安装，并用 `dsh plugin --profile desktop list --depth 0` 检查实际安装项。重开后在 Skill Factory 设置核对 Host 版本，从现有 OKR 项目打开已经完成的归并结果。禁止用删除或重置业务数据来处理安装问题。

发布需要人工确认当前构建及实际模型评测结果。构建哈希、revision 和测试计划匹配时，同一个模型的至少六条 A/B 案例须全部通过；断言是字面匹配，发布前仍需检查输出的业务含义。另开 DSH 对话检查 Skill 发现和实际工具调用。

限制：Host 重启会丢弃正在执行的任务句柄，可以通过已保存的分析、归并、评测或候选记录继续。真实模型、桌面 Host 加载、发布及新会话调用需要在部署的 DSH 中单独验证。自动化测试模型为测试替身，结果只证实应用逻辑。

## 能力架构 0.3.1 候选版

新版使用旧状态数据库中的独立 `architecture.schemaVersion` 命名空间。新增记录只通过现有事务队列写入。备份完整数据目录及个人技能目录后，进入「能力架构」点击「检查并登记旧版版本与发布」。迁移可重复执行，旧版项目、归并、评测与发布记录留在原处。回退可重新安装原来的 0.2.8，旧版忽略架构命名空间。只有回退到迁移前的精确状态时才需要在退出 DSH 后还原备份，该操作也会撤销备份之后新增的记录。

来源可直接登记文本及业务任务，或复用旧项目的已分析资料。任务、方法和证据使用标识建立多对多关系。七类决策保存证据、理由、备选和待验证假设。REUSE、REFERENCE、REJECT 不生成工程。ENHANCE 使用受管理的发布版作为比较基线，并生成独立候选，不自动替换现有资产。选填 DSH 工作区绝对路径可扩展目录盘点至工作区范围。引擎遇到目录读取不完整会停止规划。

先审批架构和能力蓝图，再开始生成。构建版本绑定独立、冻结的评测套件。每条评测比较基线和技能输出，再由模型按套件逐条判定。发布还要求全套通过、至少一个断言存在增益和人工确认。评测记录含模型、断言、评分理由及原始输出。本地测试使用替身模型，真实桌面和真实模型单独验收。

构建命令 `npm run check`，打包命令 `npm pack`。安装到 desktop profile 前退出 DSH；将下方命令中的路径改为实际安装包。
`dsh plugin --profile desktop add /path/to/dsh-personal-skill-factory-0.3.1.tgz`

## Evals v2（0.3.4）

Evals v2 通过独立的 `evalV2` 数据空间保存套件、运行与隔离工作区。旧 `architecture.evalSuites` 和旧运行记录不被迁移或覆盖。蓝图型项目发布必须使用当前构建的 v2 证据。旧版的项目走原有发布逻辑。

1. 在项目的「评测」中保存新套件。新套件保留原案例 ID、难度类别、触发方向及断言原文，包含材料正文、必需材料 ID、关键断言标注和变更理由。审批后才可运行。
2. Execution Evals 先静态校验，然后由模型审查任务材料是否足够、断言是否可观察。无效或需复核的用例不进入 A/B。两组请求共用业务内容、模型身份和输出 token 上限。Skill 组增加构建后的 Skill 正文。参考资料默认不注入，需要的业务材料应作为两组共享的冻结输入。
3. Trigger Evals 将待测构建放在独立的项目目录 `.dsh/skills`。在 DSH 把该目录加为独立工作区，每例创建全新单轮会话，选择相同模型，原样发送面板中的完整用例文本。将会话 ID 填回面板。服务端从该 Mac 的 DSH v4 会话日志核对模型、工作区、原始输入、工具调用、返回正文和结束事件。需要本机 PATH 上有 `zstd`。该流程需要手动创建桌面会话。
4. 看门禁汇总。门禁要求匹配当前构建与套件的全套触发和正例执行证据、关键断言通过、任务断言净增益。基线与 Skill 分开计 token 和耗时。触发运行保存逐步用量；预检与裁判也分别保留原始请求与统计。通过后仍需人工批准发布。

`fixtures/exhibit-v2.json` 是基于原冻结展品用例补入的合成测试材料。它是待复核的版本，不代表实机已审批。跨领域的库存与纪要用例见 `fixtures/cross-domain.json`。测试中模型替身的结果仅用于验证引擎行为。
